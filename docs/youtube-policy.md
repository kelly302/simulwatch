# YouTube の規約と画面の突き合わせ（2026-11-13。決めるための一覧）

塊 F の読み直し（docs/workflows.md 7章）で、ランキング・集計・広告が YouTube の規約に触れるおそれが出た。
規約の該当の項を1か所ずつ読み、このサイトのどの画面が当たるかを並べた。**まだ何も決めていない**。ユーザーが決めたら docs/decisions.md に書き、ここに結果を足す。

## 手順

- 読んだもの（2026-11-13。公式のページ）:
  - YouTube API Services - Developer Policies（https://developers.google.com/youtube/terms/developer-policies）の III.E.2・III.E.4・III.G・III.F.3・III.I・III.L と定義
  - Complying with YouTube's Developer Policies（手引き。https://developers.google.com/youtube/terms/developer-policies-guide）の「YouTube の API で出せる指標だけを出す」「十分な独立した価値」の節
- 読み方: WebFetch で取り、項ごとに文面と、その項が入っている見出し・箇条の前置き（「やってはいけない」の列か「許される例」の列か）を確かめた。
  **WebFetch は小さいモデルが要約して返すので、引用は一部ずつしか取れていない**（1回に約125字まで）。下の文面は要約と短い引用を元にした日本語の言い換え
- 画面の側: docs/ui.md の「画面構成」「ソートとフィルター」と、site/pages の実装（再生数・並び順・広告の枠の場所を grep）
- 重さの基準（突き合わせの前に決めた）:
  - **高**: 規約の文面にそのまま当たり、手引きにも許す例が無い
  - **中**: 規約の文面と手引きがずれている、または手引きの「許す例」と「やってはいけない例」の両方に読める
  - **低**: 手引きの許す例にそのまま入る、または表示を1つ足せば満たせる
- この手順で分からないこと: YouTube の審査（API の監査）での実際の判断、規約の改訂の履歴（ページに更新日が出ていない）、
  Terms of Service と Branding Guidelines の細部（今回は読んでいない）。法的な助言ではない

## 規約と手引きの該当の項（言い換え）

| 項 | 中身 |
| --- | --- |
| 規約 III.E.2.a 集計 | API のデータを集計してよいのは、YouTube と契約した同じ content owner のチャンネルの間だけ。集計したものはその content owner だけが見られるようにする。文面は「API Data」全体（認可されたデータに限っていない） |
| 規約 III.E.2.b | YouTube の利用や収益など、YouTube の事業を探る目的で集計しない |
| 規約 III.E.4.c・d | 保存した API のデータは30日以内に消すか取り直す |
| 規約 III.E.4.e・f | 保存したデータは YouTube の今の値に合わせる（再生数の更新など）。画面には最新の値を出す。昔の値を出すなら、いつの値かが正しく分かる形で |
| 規約 III.E.4.h 派生の指標 | API のデータを自前で計算した似た値で置き換えない。API のデータから新しい指標・派生した指標を作らない。API のデータと並べて YouTube 由来でない数を出すときは、YouTube 由来でないと**はっきり目立つように**書く |
| 規約 III.G.1.d 広告 | YouTube の API のデータを含むページで広告を売るには、YouTube から得ていない情報が同じページにあり、**YouTube のデータを取り除いてもそれだけで広告に見合う独立した価値**があること |
| 手引き「やってはいけない」 | 別々のチャンネルの間で再生数を順位づけ・追跡してチャンネルの成績を競わせる、配信者の対抗心をあおる（gamify） |
| 手引き「やってはいけない」 | 認可された（OAuth の）データを、その持ち主だけが見る形でなく集計して出す |
| 手引き「やってはいけない」 | YouTube の API のデータをほかのデータと混ぜ合わせる（見出しは「YouTube の API で出せる指標だけを出す」） |
| 手引き「やってはいけない」 | 再生数などを、API が返す数と違う数で出す |
| 手引き「許される指標」 | YouTube の API のデータだけを、足す・引く・平均・掛ける・割るの簡単な計算でまとめたもの。例に「動画・チャンネルのまとまりの合計再生数」「再生数などで並べた、最も見られた動画・チャンネル」 |
| 手引き「独立した価値」 | 今の YouTube の API では得られない機能を足すこと。許す例は、ほかのサービスの動画と並べてはっきり区別する検索 |
| 規約 III.L | 分析の用途で審査を通った開発者向けの追加の決まり（2026-06-01 から）。このサイトは当たらない |

規約 III.E.2.a と手引きはずれている。規約の文面は API のデータ全体の集計を同じ content owner の中に限るが、
手引きは同じ趣旨を「認可された（OAuth の）データ」の話として書き、公開のデータの合計や再生数順の並びを「許される指標」に挙げている。
このサイトのデータは API キーで取る公開のデータ（認可されていないデータ）なので、手引きに沿えば集計は許される側、規約の文面だけ読めば当たる側になる。

### 広告のページごとの見立て（7）

基準は「YouTube のデータを取り除いても、残った情報だけで広告に見合う価値があるか」。

| ページ | YouTube のデータを取り除いて残るもの | 見立て |
| --- | --- | --- |
| 作品ページ | 作品名・作品画像（AniList）・種類・放送年・制作国・シリーズのまとめ（外部DB）、観た配信者の名前と所属（事務所の公式サイトの名簿） | 一番強い。ただし「どの配信者がこの作品を観たか」の結び付きは YouTube の題名から作っている。YouTube から得た情報かどうかは灰色 |
| 配信者ページ | 配信者の名前・所属（公式サイト）、観た作品の一覧と作品画像（外部DB） | 作品ページと同じ。中 |
| トップ | よく同時視聴される作品の棚（作品情報）。ランキングと「すべての同時視聴」は YouTube のデータそのもの | 弱い。ページの大半が YouTube のデータ |
| ランキング（今は広告の枠なし） | ほぼ何も残らない | 広告を置かない |

## 決め方の選択肢（勧めは太字）

1. 作品ページの「観た配信者」の既定の並び: **最終視聴日（または名前）を既定にし、再生数は表示だけにするか、並び順の選択から外す** ／ このまま
2. ランキング: **動画単位のまま残し、配信者の対抗に読めない見せ方にする**（見出しを「よく見られた同時視聴の枠」などに、説明に「動画の再生数の順」と書く。配信者名は残す） ／ 名前も「ランキング」のまま残す ／ ランキングをやめる（主要指標の使い道が変わる）
3. 作品ページの最高・合計再生数: **手引きの許す例に沿うので残す**（規約の文面との差は承知のうえ） ／ 合計を外す ／ 両方外す
4. 自前の数の表示: **作品ページの集計の欄と /about に「配信者数・枠数は当サイトの集計で、YouTube の数ではない」と書く**
5. 広告: **CLAUDE.md の広告の根拠から「集計値」を外し、作品情報だけを根拠にする。広告は作品ページ・配信者ページにだけ置き、トップから外す**（ランキングにも置かない） ／ 今の3ページのまま
6. 生レスポンスの日数: **29日**（決めたら G のライフサイクルの設定に伝える） ／ 30日

1・2・4・5 を勧めのとおりにすると、規約の文面と手引きのどちらに沿って読んでも残るおそれは 3 と 9（集計と結び付けの解釈）になる。
3 と 9 はサイトの中心の機能なので、手引きの読み方（公開のデータの簡単な集計は許される）に立つことになる。

## 30日の決まりで取り直す・消すもの（2026-11-13 に数えた）

規約 III.E.4.d: ログインなしで取ったデータ（このサイトのデータは全部これ）は、30日を超えて持たない。30日を過ぎたら**消すか取り直す**。
III.E.4.b の例: 再生数などの統計は30日を超えて持たない。動画が削除されていないかを30日ごとに確かめる。III.E.4.e: 題名などの変更と再生数はなるべく早く反映する。
規約には「動画の ID なら無期限に持ってよい」という例外は書かれていない（取り直すには ID が要るので、取り直す前提で ID を持つのは避けられない）。

数え方: 本体の DB（data/db.sqlite。読むだけ。user_version 11。candidates の表はまだ無い）を 2026-11-13 に node:sqlite で数えた。30日は `datetime('now','-30 days')` より前。

| 置き場所 | 中身 | 件数・古さ | 今の取り直し | 見立て |
| --- | --- | --- | --- | --- |
| watch_events（同時視聴の枠） | 題名・概要欄・サムネの URL・開始と終了・状態・再生数 | 7,727枠。最後の取り直しは全部 2026-10-29 | 日次の refresh が全枠を videos.list で取り直す（消えた枠も含む） | 日次が動けば満たす。**11-28 までに refresh を流す必要**（段6の「もう一度 refresh」） |

直し方の案（2026-11-13 にユーザーが塊として作ると決めた。D-12。下の「済んだこと」）:

1. videos_seen: 30日で1周するように少しずつ videos.list で取り直す（355,373本 ÷ 50本 ≈ 7,108ユニットを30日に分けて**1日 約240ユニット**。今の日次の約800に足しても上限の8,400に収まる）。
   消えた動画は題名を消す。代わりに「30日より古い行は題名を消して ID と判定の結果だけ残す」もできるが、語彙を変えたときの判定のやり直しと候補選びのたびに題名を取り直すことになる
2. candidates: 枠にならなかった候補は、30日ごとに取り直すか、題名・概要欄・再生数を消す
3. streamers: 卒業した配信者も roster で取り直す（数ユニット）
4. watch_events: アーカイブが消えた枠は、30日たったら題名・概要欄・サムネ・再生数を消す（今は「行は残す」で中身も残る。今は0件）
5. 手元のファイル: data/raw・DB の写し・data/ai の作業フォルダ・ログのうち30日を超えたものを消す決まりを作り、今あるものを片づける（消すのはユーザーの確認のあと。経緯の記録に使っているものがある）
