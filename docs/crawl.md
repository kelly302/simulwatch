## 取得パイプライン

    1. discover  同時視聴キーワードで動画検索し、ヒットした
                 チャンネルを追跡対象に自動登録する（Phase 5。まだ作っていない）
    2. crawl     追跡対象チャンネルを巡回（検索APIより低コスト）
    3. detect    タイトル・概要欄から同時視聴枠を判定
    4. extract   作品名・話数の候補文字列を切り出す
    5. resolve   Annict / AniList（アニメ）、Wikipedia → Wikidata（実写・特撮・海外作品）に照会して作品ID・話数を確定
    6. publish   解決済みのみ作品ページに反映（site:data → site:build。集計値は site:data が書き出すたびに作り直す）
    7. refresh   再生数・状態の取り直しとアーカイブ死活チェック
    8. retention 30日の決まり（D-12）。巡回で見た動画の題名の取り直しと、取り直さないものの中身を消す（下の「30日の決まり」）

### crawl の分担（RSS と API の併用）

    日次       playlistItems で全チャンネルを巡回する（uploads の先頭50件とメン限の再生リスト）。全枠の再生数・状態を videos.list で取り直す
    （流さない） チャンネルRSSで投稿済み動画の差分を検知し、予定枠と LIVE の状態を API で取る（crawl:hourly）

- **定期実行は日次だけ**（日本時間 05:23。2026-10-27・10-30 の決定 D-01。docs/workflows.md）。こまめな巡回（crawl:hourly）は流さない。
  予定枠・配信中の枠はサイトに出さない（`refresh` が状態を取り直すので DB には入り、終わってから名寄せ・判定されて出る）。RSS（直近15件ほど）と playlistItems の順繰りで拾えるものは、日次の uploads の先頭50件で拾える。
  crawl:hourly のコードと config/crawl.yaml の `hourly` は、2時間ごとに戻すときのために残す（docs/workflows.md の付録。2026-10-11 から 10-27 までは2時間ごと、当初は毎時）

- RSS は直近15件程度しか返さない。予定枠は RSS にも載る（2026-09-23 の実データで予定枠40件すべて）。
  当初の「RSS に予定枠が載らない」という前提はゲート1で撤回した。
- crawl:hourly を流していたころは、予定枠の鮮度を API 側でも担保するため、巡回のたびの playlistItems 順繰りを各チャンネル12時間ごとに縮小して残していた。
  浮いた予算は Tier 2（Phase 5）用に確保する。

実装上の分担（`config/crawl.yaml` で調整する）:

    （流さない） crawl:hourly（D-01。2時間ごとに戻すときのために残す。名前は毎時のころのまま）
                       1. 全チャンネルの RSS（クォータ0）
                       2. playlistItems をチャンネルの一部ずつ（各チャンネルを12時間ごと）
                       3. 判定 → ヒットだけ videos.list → WatchEvent
                       4. upcoming / live の枠を videos.list で取り直す（開始時刻・状態を上書き）
    日次 roster        公式サイトと Tier 1 を同期、channels.list でアイコン更新
    日次 crawl:daily   全チャンネルの uploads 先頭50件 ＋ メン限プレイリスト（UUMO…）
                       ＋ 詳細を取り損ねたヒットの回収 ＋ 過去分の遡り（予算内でページを進める）
    日次 refresh       全 WatchEvent の再生数・状態の取り直しとアーカイブ死活チェック（返ってきた枠の動画は videos_seen の題名と確かめた時刻も）
    日次 candidates    続きの回の候補の選定と詳細（判定に回す候補の詳細が25日より古ければ取り直す）
    日次 retention     videos_seen の題名を古いものから取り直す・終わった候補の詳細と、消えて25日たった枠の中身を消す（D-12）

### detect の実装ルール

- 語彙・正規化は `config/detect.yaml`。語彙を変えると判定バージョンが変わり、次に見たときに再判定される。
  `detect:rerun` で保存済みタイトルを API なしで再判定できる（概要欄は保存していないのでタイトルのみ）
- 概要欄は行単位で見る。**その枠自体を指す語（今日・本日・今回・この配信 など、`line_require`）を含む行だけ**をヒットにする。
  否定語（ご遠慮・禁止・NG など）や二次利用ルール（ガイドライン・切り抜き など）を含む行は無視する
- 詳細を取って WatchEvent を作る時点で、取得したタイトル・概要欄を今の語彙で判定し直す（古いルールでヒットした保留分が入らないように）
- `detect:rerun` は既存の WatchEvent も判定し直し、当たらなくなった枠は `excluded_at` を立てて外す（行は消さない）
- 概要欄の**定型文**は無視する。同じチャンネルの動画のうち `template_min_repeats` 本以上に出る行
  （チャンネル紹介・メンバー特典の一覧など）。実データでは概要欄ヒットの大半がこれだった
- ライブ配信でない動画も同時視聴枠にする（`reject.require_live: false`）。Twitch での同時視聴の再アップがあるため。
  started_at は publishedAt で代用し、`started_at_source = published_at` と記録する
- is_members_only は「メン限プレイリスト（UUMO…）に載っている」か「タイトルにメン限の語がある」で立てる
- **「同時視聴前」を含むタイトルは同時視聴枠にしない**（「同時視聴前に待ち合わせ！」などの前座・待機枠。ゲート2で17枠を外した）
- **英語のタイトル**（2026-10-02。NIJISANJI EN・hololive EN を足したとき、保存済みの全タイトル（約29万本）で当たり方を確かめた）: 「watchalong」に加えて
  「watching party」（大空スバルの枠など16本。すべて同時視聴）・「movie night」（EN の9本。すべて同時視聴）・タイトルの先頭か括弧の直後の「watching」
  （25本中24本が同時視聴。外れは「Watching My Own Stream」）。文中の watching（「BIG ROCO IS WATCHING YOU」）は拾わない。
  「watch party」は eスポーツの観戦が大半（59本中、作品は姫森ルーナの4本）なので入れない。メン限の語に「member's only」「MEMBERS STREAM」なども足した
- **題名に同時視聴の語が無かった同時視聴**（2026-10-19。続きの回の計測で、miss に残っていた動画から見つけた。docs/ai-runs.md）: 誤字の「watchalon」（「watch alone」は除く）・「watchlong」、
  インドネシア語の「nobar」（「Nobara」は除く）、「映画鑑賞」を足した（26本。見た限りすべて同時視聴）。
  「let's watch」「一緒に/みんなで観る」「視聴会」は入れない（同時視聴でない動画（自分の歌の公開・Steam のセール・告知など）が混ざる。2026-10-19 の時点では予定枠・配信中の枠が AI の判定を待たずに出たので、
  語彙に入れるとそのまま「これから始まる枠」に出た。D-01 で予定枠は出さなくなった）（弱い語は 2026-11-13 から続きの回の候補として AI の判定役に回す。config/candidates.yaml の weak_words。D-04・docs/ai-ops.md 3-1）。「鑑賞」単独は切り抜き鑑賞会・PV 鑑賞会が大半。**語彙に足すのは、見た限りほぼ全部が同時視聴の語だけにする**
- `line_require` に「を見ます」「を観ます」を入れている（概要欄の「A、B、Cを見ます」を名寄せで作品名の列挙として使うため）。
  2026-09-24 に生レスポンスに残っている全動画（142,152本）で比べ、概要欄での検出は20本のまま増えなかった

### アーカイブ消失の判定

- videos.list に返ってこない、または privacyStatus が public 以外（限定公開・非公開）なら
  `archive_gone_at` を立てて一覧から消す。行は消さない
- 日次の refresh は消失済みの枠も見に行き、また見られるようになっていれば戻す
- 1バッチ（10件以上）の半分超が欠けたら API 側の異常とみなして消失判定を見送る
  （取得失敗時に既存データを消さない）
- 消えて25日（`retention.act_after_days`）を過ぎた枠は、日次の retention が題名・概要欄・サムネの URL・再生数を消す（purged_at。D-12）。
  行・判定・作品の結び付きは残し、見られるようになったら refresh が中身を入れ直す

同定に失敗した枠は黙って捨てず、**修正対象のエラーとして一覧できるようにする**。
同時視聴が1件もない作品はページを作らない。

### unresolved の確認方法

- unresolved は R2 の JSON に出力し、**ローカルの CLI** で一覧・件数・頻出パターンを確認する（→ D-08 で R2 に置かず、DB の写しをローカルの CLI で見る形に変更予定・未実装）。
- GitHub Issues への自動起票はしない。公開サイトにも出さない。

## 30日の決まり（YouTube の API の規約 III.E.4。決定 D-12。2026-11-13）

ログインなしで取った YouTube の API のデータ（このサイトのデータは全部これ）は30日を超えて持たない。過ぎたら**取り直すか消す**。
DB の中のものは、最後に API で確かめてから **25日**（config/crawl.yaml の `retention.act_after_days`。30日との差の5日は日次が止まった日の余白）を過ぎたら取り直すか消す。
実装は src/retention/（`retention`・`retention:status`・`retention:files`）と、refresh・roster・candidates:fetch・巡回の中。

| 置き場所 | 取り直す・消す | どこで |
| --- | --- | --- |
| watch_events（同時視聴の枠） | 全枠を毎日取り直す。アーカイブが消えて25日を過ぎた枠は題名・概要欄・サムネの URL・再生数を消す（purged_at）。行・判定・作品の結び付き・時刻・状態は残し、見られるようになったら入れ直す | refresh・retention |
| videos_seen（巡回で見た全部の動画の題名・公開日） | 題名を最後に確かめた時刻（refreshed_at）の古いものから videos.list で取り直す。1日の本数は「題名を持つ行 ÷ 25」（約35.5万本で約14,200本＝約285ユニット）と「25日を過ぎた行」の多いほう（上限 `videos_seen_max_units` 1,500ユニット）。返ってこない・公開でない動画は題名を空文字に・公開日を NULL に（gone_at）。題名が変わったら下のとおり判定し直す | retention（巡回で同じ題名を見た・refresh で枠の動画を取り直したときも refreshed_at を進める） |
| candidates（続きの回の候補） | 判定に回す候補（ready・hold）は、詳細が25日より古い・無ければ取り直す（状態はそのまま）。終わった候補（detected・framed・not_watchalong）は詳細を取ってから25日で、取れない候補（unavailable）はすぐに、題名・概要欄・サムネの URL・再生数を消す（cleared_at） | candidates:fetch・retention |
| streamers（チャンネル名・アイコン） | 巡回を止めた配信者も含めて毎日 channels.list で取り直す。返ってこないチャンネルは、最後に返ってから25日を過ぎたらアイコンとチャンネル名を消す | roster |
| 手元の data/（生レスポンス・DB の写し・AI の作業フォルダ・audit・review・analysis・ログ・unresolved.json・site-data.json） | `retention:files` で30日を超えたものを一覧にする。消すのは `--delete` のときだけ（中のファイルが全部古い項目だけ）。自動では消さない | 人が起動する |
| R2 の raw/ | ライフサイクルで消す（日数は docs/deploy.md 6-4・docs/youtube-policy.md の選択肢6） | R2 |

- **videos_seen の題名が変わったとき**: 巡回（judgeCandidates）と同じく判定し直す。同時視聴の枠がある動画は判定し直さず題名だけ今のものにする（巡回も枠は判定し直さず、refresh が枠を取り直す）。
  判定は題名と概要欄。概要欄の定型文は、その回に取った同じチャンネルの動画の概要欄から作る（巡回は uploads の先頭の約50本で作る。数が違うので定型文の見つかり方は少し違う）。
  新しく当たった動画は 'hit' にし、次の日の crawl:daily の orphan hits（か detect:fetch）が枠にする。語彙のバージョンだけが変わった動画は判定し直さない（detect:rerun の仕事）
- **並び**: 確かめた日（UTC の日付）の古い順、同じ日の中は動画の ID の順。時刻の順だと遡りで続けて見た1つのチャンネルの動画が固まり（2026-11-13 の写しで最初の750本のうち748本が1チャンネル）、
  チャンネルごと消えたときにバッチが全部欠けて「API の異常」とみなし、いつまでも消せない
- **API の異常の見なし**: refresh と同じ（1バッチ10本以上で半分超が返らなければ消さない。channels.list も同じ）
- **クォータ**: 定期実行のジョブの上限（8,400）の中。尽きたら止めて取れたぶんを書き、残りは次の日。初回は 25日を過ぎた行が約33万本あるので、1,500ユニット/日で約5日かけて追いつく
- **ジョブが止まったとき**: `retention:status` が「25日以上 refresh で取り直していない枠」「30日を過ぎた videos_seen の行」を出す。refresh が止まったままの枠の中身は自動では消さない（サイトから枠が消えるので、人が直す）

## 実行環境と巡回頻度

- 自宅PCの起動を前提にしない。GitHub Actions の schedule で回す
- 無料枠で完結させる
- 定期実行は日次だけ（D-01。それまでは2時間ごと。巡回は最短1時間ごとまで許容する作り）。YouTube の10,000ユニット/日に収める
  （playlistItems.list / videos.list は1ユニット、search は100ユニット）
- 再生数の取り直しと集計値の再生成は日次でよい
- 予定枠は開始時刻が変わるので、取り直すたびに上書きする（日次の refresh）

## 運用（schedule）

### schedule の60日自動停止への対策

公開リポジトリでは、60日間コミットがないと GitHub Actions の schedule が自動で止まる。
データは R2 に置いてコミットしないため、このままだと止まる。

- まずは**月1回の軽いコミット**（keepalive ワークフロー）で様子を見る。
- それでも止まるようなら、Cloudflare Workers Cron から workflow_dispatch で
  起動する方式に切り替える。
